# 티어리스트 화면 추가

## Context

챔피언별 성능 티어와, 그 챔피언에게 잘 맞는 증강·아이템을 성적순으로 보여주는 화면이 없다. 사용자는 blitz.gg·op.gg가 하는 일을 앱 안에서 하길 원한다 — 챔피언을 S/A/B/C/D로 묶어 보여주고, 챔피언을 누르면 그에 어울리는 증강과 아이템을 성적순으로 펼치는 것.

가장 큰 미지수는 "그 데이터를 어디서 가져오는가"였다. 조사 결과:

- **Riot이 Mayhem 계열 match-v5를 403으로 막아뒀다.** 그래서 op.gg·u.gg·lolalytics·metasrc 어디도 칼바람 광란 승률을 주지 못한다(metasrc는 ARAM+Arena를 합성해 만든 가짜다). op.gg 페이지에 퍼센트 숫자가 하나도 없는 게 그 증거다.
- 승률을 실제로 주는 곳은 **aram.gg 백엔드(`data.dtodo.cn`)** 하나뿐이고, 아레나는 **Blitz 내부 API(`data.v2.iesdev.com`)** 가 준다. 둘 다 인증 없이 열려 있고 일 단위로 갱신된다.
- **클래식(협곡 광란)은 어느 소스에도 없다** → 필터에서 제외 확정.

의도한 결과: 칼바람·아레나 두 모드에서 챔피언 티어표를 보고, 챔피언을 눌러 그 챔피언의 상위 증강(희귀도별)과 상위 아이템(아레나는 프리즘 포함)을 표본수와 함께 확인할 수 있다.

## 확정된 결정 (사용자 선택)

| 항목 | 결정 |
|---|---|
| 탭 아이콘 | `chart.bar` (iOS26 미만 폴백은 MaterialIcons `bar-chart`) |
| 필터 | 칼바람 · 아레나 **2개만** |
| 데이터 배송 | **빌드타임 스크립트 → 정적 JSON 번들** (런타임 fetch 아님) |
| 그룹 컷 | 백분위 S=상위10% / A=~30% / B=~60% / C=~85% / D=나머지 |

백분위 컷 실측: 칼바람 17/34/51/43/26, 아레나 17/34/52/43/26 — 두 모드 모두 균등하게 찬다. 절대 승률 구간(53%/51.5%/…)은 D에 50명이 몰려 탈락시켰다.

## 데이터 소스 — 전부 curl로 실측 검증됨

### 칼바람 (ARAM Mayhem)

```
GET https://data.dtodo.cn/api/client/v1/config
  → { dataVersion:"16.17.4", gamePatch:"16.17", generatedAt }

GET .../api/client/v1/data/{dataVersion}/champions.json
  → { total:172, data:[ { id:17, alias:"Teemo",
        stats:{ tier, winRate:0.5349, pickRate:0.1354, source:"tencent", region:"CN", date } } ] }
      ※ 최상위 키는 `data` (`champions` 아님). winRate 172명 전원 존재, 0.406~0.566

GET .../api/client/v1/data/{dataVersion}/champions/{championId}.json
  → { augments:[ { id:1002, stats:{ wins, games, winRate, pickRate,
                     winRateMinimumGames:255, winRateSource:"aramgg-client-upload" } } ],
      items:[],                                   ← 항상 비어 있음. 쓰지 않는다
      build:{ queueId:450, situationalItems:[ { id:3036, games:41843, wins:22060 } ] } }
```

### 아레나

```
GET https://data.v2.iesdev.com/api/v1/query_objects/prod/lol/arena_champions
  → { data:[ { champion_id:"3", stats:{ avg_placement:3.308, top_1_percent:0.2156,
        pick_rate, num_games, win_rate:null } } ] }                      # 173명

GET .../arena_champion?champion_id={id}
  → { data:[ { data:{ augments:{ "39":{ avg_placement, top_1_percent, num_games } },   # 170개
                      items:{ "447108":{ avg_placement, top_1_percent, num_games } } } } ] }  # 93개
```

**아레나는 `win_rate`가 구조적으로 null이다.** 8인 2인팀 배틀로얄이라 지표가 `avg_placement`(평균 등수, 낮을수록 좋음)와 `top_1_percent`(1등률)다. 그룹화는 `avg_placement` 기준 — 두 지표는 173명 중 84명이 순위 20계단 이상 어긋나고, 평균 등수가 아레나 티어의 표준 지표다. 1등률은 카드에 함께 표시만 한다.

### ID 매핑

```
GET https://raw.communitydragon.org/latest/plugins/rcp-be-lol-game-data/global/{ko_kr|en_us}/v1/cherry-augments.json
  → 657개  { id, augmentNameId, nameTRA, augmentSmallIconPath }
```

| 대상 | 조인 경로 | 실측 |
|---|---|---|
| 챔피언 | 숫자 id → 앱 `champions.ko.json`의 **`key`** | 172/172 (`805` Locke만 미스 — 앱 데이터가 구버전) |
| 칼바람 증강 | dtodo id → cherry `augmentNameId` → 앱 `augments.ko.json` → **`.id`** | **100%** |
| 아레나 증강 | Blitz 숫자키 → cherry `augmentSmallIconPath` basename(소문자) → 앱 `arena/augments.ko.json` → **`.id`** | 89.6% |
| 모든 아이템 | 숫자키 → CDragon `items.json` → **이름·아이콘 직접 구움** | **100%** |

## 두 가지 함정 (실측으로 확인, 반드시 지킬 것)

**1. `situationalItems[].winRate` 필드는 쓰레기다.** 음수까지 나온다:

```
id=3036  games=41843 wins=22060  wins/games=0.5272  winRate필드= 0.0834
id=3153  games=11136 wins= 5775  wins/games=0.5186  winRate필드=-0.1884   ← 음수
```

→ **반드시 `wins / games`로 직접 계산한다.** 정규화 점수로 보이는 별개 값이다.

**2. 칼바람 아이템은 모드가 다르다.** `build.queueId`가 3개 전부 **450(일반 칼바람)** 이고 2400(광란)이 아니다. 증강은 광란 기준, 아이템은 일반 칼바람 기준의 혼합이 된다.

대안인 Blitz `aram_mayhem_champion.items`는 진짜 광란 데이터지만 `{tier:1~5}`만 줘서 정렬하면 동점이 수십 개다 — "승률 높은 아이템"이라는 요구를 만족시키지 못하고 요청만 172건 늘어난다. **dtodo를 쓰되 출처에 "아이템은 일반 칼바람(ARAM) 통계"라고 명시**한다.

## 아이템은 CDragon 사전으로 통일한다

앱 `items.ko.json`에 조인하면 아레나 상위 아이템의 **38%가 빠진다** — 케이틀린 상위 12개 중 `224403`(황금 뒤집개, 1등 아이템)과 `443056`(불사대마왕의 왕관)이 미스. 둘 다 아레나 전용 아이템이라 앱 데이터에 없는 게 당연하다. 모든 챔피언의 1등 아이템이 안 보이는 건 제품 결함이다.

CDragon `items.json`은 이 12개를 **12/12 커버**한다. 14명 샘플 실측: 유니크 아이템 40개 = **4.5KB**, CDragon 미커버 0개. 172명으로 가도 유니크는 금방 포화돼 ko/en 합쳐 ~50KB.

→ **칼바람·아레나·프리즘 아이템 전부를 CDragon 이름/아이콘 사전 하나로 굽는다.** 이게 앱 조인보다 오히려 게으르다:
- `22`/`44` 접두사 제거 로직 삭제
- 앱 `items.ko.json` / `prismatic-items.ko.json` 조인 삭제
- 프리즘 구분은 `id.startsWith('447')` 하나
- 결손 0%

아이콘은 기존 `cdragonItemIconUrl(iconPath)`가 그대로 처리한다(프리즘이 이미 이 방식).

증강은 다르다 — 칼바람 100% 조인되고, 앱 데이터에 **사람이 손본 정제 설명**이 있어 CDragon 원문보다 낫다. 아레나 11% 결손은 앱 아레나 증강 데이터가 오래된 별개 문제이고, 희귀도별 상위 4개를 채우는 데 지장 없다 → 조인 실패분은 버리고 `ponytail:` 주석으로 남긴다.

## 출력 스키마

`src/features/tierlist/data/tierlist.json` — 단일 파일, **로케일 무관**(숫자 id + 숫자 값만).

```jsonc
{
  "patch": "16.17",
  "date": "2026-09-06",            // 소스 집계일
  "generatedAt": "2026-09-08T...", // 스크립트 실행 시각
  "aram": [                        // score 내림차순 정렬 완료
    { "key": "17",
      "score": 0.5349,             // winRate
      "sub": 0.1354,               // pickRate
      "augments": [ { "id": "erosion", "score": 0.5601, "games": 14112 } ],
      "items":    [ { "id": "4645",   "score": 0.5053, "games": 32091 } ] }
  ],
  "arena": [                       // score 오름차순 정렬 완료
    { "key": "17",
      "score": 3.58,               // avg_placement
      "sub": 0.1356,               // top_1_percent
      "augments":  [ ... ],
      "items":     [ ... ],
      "prismatic": [ ... ] }       // 아레나 전용
  ]
}
```

`tierlist-items.ko.json` / `.en.json` — `[{ id, name, iconPath }]`, 위 JSON이 참조하는 아이템만.

**배열은 스크립트가 이미 정렬해서 내보낸다** → 앱은 절대 sort하지 않는다(모드별 정렬 방향 분기가 사라진다). 증강 희귀도도 담지 않는다 — 앱이 조인한 레코드의 `.rarity`로 그룹핑.

크기 손잡이는 스크립트 상단 상수 3개: `N_AUG=4`(희귀도별) / `N_ITEM=6` / `N_PRISM=5` → 약 350KB + 아이템 사전 50KB. 앱이 이미 1.2MB JSON을 싣고 있어 +33%.

## 표본 필터

```ts
// 칼바람 증강 — dtodo가 임계값을 같이 준다
if (s.winRate == null || (s.games ?? 0) < (s.winRateMinimumGames ?? 0)) skip;
// 아레나 — Blitz는 임계값을 주지 않는다
if ((v.num_games ?? 0) < 200) skip;
```

**순서가 중요하다: 표본 필터 → 조인 실패 제거 → 정렬 → 상위 N개 slice.** 조인 실패를 먼저 버려야 항상 N개가 찬다(아레나 증강 10%가 조인 실패라 slice를 먼저 하면 3개짜리 그룹이 나온다).

표본수는 모달의 증강·아이템 행에만 노출한다(`56.0% · 14,112판`). 목록 카드에는 넣지 않는다 — 칼바람 챔피언 레벨은 `wins`/`games`가 null이라 표본수가 아예 없어 아레나와 비대칭이 된다.

## 구현 순서

1. **스크립트 먼저.** `npx tsx scripts/fetch-data/fetch-tierlist.ts 5`로 5챔피언 스모크 → 스키마·조인율 확인 → 전량 실행(344요청, 순차 + 150ms 딜레이, 4~8분).
   - `fetchJson(url, tries=3)` 500ms·1500ms 백오프, 3연속 실패 시 그 챔피언은 해당 모드에서만 스킵
   - sanity 가드 `if (aram.length < 150 || arena.length < 150) throw` — 소스가 반쯤 죽은 날 좋은 JSON을 덮어쓰지 않게
   - 종료 시 요약 출력: 모드별 챔피언 수 / 스킵 목록 / 조인 실패 카운트
2. **`scripts/check-tierlist.ts`** — `check-build-storage.ts`와 같은 방식(`node:assert/strict`, 프레임워크 없음):
   - 챔피언 수 ≥ 150(양 모드), 모든 `key` ∈ `champions.ko.json`
   - 정렬 방향(aram desc / arena asc), `score` 범위(aram 0.2~0.8 / arena 1~8), `games ≥ 1`
   - 모든 `augments[].id`가 해당 모드 증강 풀에 존재, 모든 `items[].id` ∈ 아이템 사전
   - 챔피언마다 희귀도 3종이 각각 ≥ 1개
   - `tierSections()` 버킷 합 = n, 빈 버킷 없음
3. **탭 3파일**(라우트 2 + `app-tabs`) → 빈 화면이라도 탭이 뜨는지 확인
4. **목록 화면** → 세그먼트 · S~D 섹션 · 4열 격자 · 출처 푸터
5. **모달** → 루트 라우트 등록 + 화면
6. 계획 문서를 `docs/plans/2026-09-08-티어리스트-화면.md`로 저장 (CLAUDE.md 규칙)

## 알려진 한계 (`ponytail:` 주석으로 코드에 남길 것)

- **칼바람 아이템은 일반 ARAM(450) 통계** — 광란(2400) 아이템 승률은 어느 소스에도 없다. Blitz가 티어만 주는데 정렬 불가.

## 구현 후 변경 (2026-09-08 실제 반영분)

계획과 달라진 지점만 기록한다. 검증 기록은 `docs/verification/2026-09-08-티어리스트-화면.md`.

1. **표본 하한을 칼바람 아이템까지 확대.** 계획에는 아레나만 `num_games >= 200` 을 걸었는데,
   시뮬레이터 검증에서 그웬의 아이템 1위가 `리안드리의 고통 66.2% · 71판` 으로 나왔다
   (1,042판짜리 61.4% 를 제쳤다). dtodo 가 임계값을 주는 건 **증강뿐**이고 아이템에는 안 준다.
   `MIN_GAMES = 200` 상수 하나로 통일하고 `check-tierlist.ts` 에 같은 하한 assert 를 넣었다.

2. **모드 세그먼트는 Host 에 실제 치수를 준다.** SwiftUI segmented Picker 가 폭을 주장하지
   않아 좌측에 쪼그라들었고, `matchContents` 도 `frame({ maxWidth })` 도 못 폈다.
   `useWindowDimensions()` 로 `width: 화면폭 - 인셋*2`, `height: 32` 를 Host style 에 직접 준다.

3. **선택 인디케이터는 회색(네이티브 기본)으로 둔다.** iOS 26 의 `.pickerStyle(.segmented)` 는
   `tint` 를 선택 배경에 적용하지 않는다. 민트로 맞추려면 RN 커스텀으로 내려가야 해서 포기.

4. **`custom-tabs.tsx` 의 `+` 버튼을 맨 뒤로 옮겼다.** 4칸이 되면서 중앙 원형 버튼이 정중앙을
   벗어나므로, iOS 26+ `NativeTabs` 순서(메인/티어리스트/마이페이지/+)와 맞췄다.

5. **파일 수는 계획대로 11 신규 + 4 수정.** `types.ts`·`components/` 는 만들지 않았다 —
   `DetailCardRow`·`AugmentTile`·`RemoteImage` 로 증강·아이템·프리즘 세 목록이 전부 커버됐다.
